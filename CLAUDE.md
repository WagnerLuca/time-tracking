# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Full-stack multi-organization time tracking app. ASP.NET Core Web API backend (`backend/`) + SvelteKit frontend (`frontend/`). Domain covers time entries, work schedules, absences (vacation/sick), holidays, approval requests, notifications, and organization/group-scoped permissions.

- **Backend**: ASP.NET Core, **.NET 10** (`net10.0`), C#.
- **Frontend**: SvelteKit + **Svelte 5 (runes)**, TypeScript, SSR via `adapter-node`, Tailwind CSS 4 with its own theme (no component library), styled with the Wagner Luca design system: `src/app.css` has a Tailwind `@theme` whose colours (`base-100/200/300`, `base-content`, `primary`, `secondary`, `accent`, `neutral`, `info/success/warning/error` + `-content`) are `var()`s onto `@wagnerluca/ui/tokens.css` (primary = `time` accent), so opacity modifiers like `text-base-content/60` work in both modes. The component classes the markup uses (`btn`, `card`, `input`, `badge`, `modal`, `tab`, `menu`, …) are hand-written in `src/lib/theme/components.css` (`@layer components`, utilities still win) — add a class there when markup needs a new one. Light/dark is the `.dark` class on `<html>` under the shared `wl-theme` key (`theme.svelte.ts` + the pre-paint script in `app.html`); the tokens flip on it. `@wagnerluca/ui` is an **optional** dependency from GitHub Packages — with `NODE_AUTH_TOKEN` (read:packages; BuildKit secret in Docker, `GHP_READ_TOKEN` in CI) it is installed and used; without it npm skips it and `vite.config.ts` aliases `@wagnerluca/ui/tokens.css` to the bundled copy `src/lib/theme/wl-tokens.fallback.css` (the build logs which one). After upgrading the package run `npm run tokens:sync`. Dependabot ignores it (no GitHub Packages registry in `.github/dependabot.yml`) — update it by hand.
- **DB**: PostgreSQL 16 in production; **in-memory EF Core provider in local dev** (no Postgres needed to run the backend).

## Commands

### Backend (`cd backend`)
- Run with hot reload: `dotnet watch run` (or `dotnet run`) → http://localhost:7000, Swagger at `/swagger`
- Build: `dotnet build`
- Uses in-memory DB by default in Development (`UseInMemoryDatabase: true` in `appsettings.Development.json`), auto-seeded on startup.

### Backend tests (`cd backend/tests/TimeTracking.Api.Tests`)
- All tests: `dotnet test`
- Single test/class: `dotnet test --filter "FullyQualifiedName~AuthControllerTests"` or `--filter "DisplayName~specific test name"`
- Tests are **integration tests** using `WebApplicationFactory`, xUnit + FluentAssertions, with `ASPNETCORE_ENVIRONMENT=Testing` (rate limiting disabled in that env). Two factories:
  - `Infrastructure/TimeTrackingApiFactory.cs` — EF **InMemory** (fast; one DB per test class). InMemory enforces no unique indexes, transactions, DateTime kinds or RLS.
  - `Infrastructure/PostgresApiFactory.cs` + `[Collection(PostgresCollection.Name)]` (tests under `Postgres/`) — a real **PostgreSQL container via Testcontainers** (needs Docker), connecting as a non-superuser app role so row-level security applies; runs the real migrations + seed. Put anything touching indexes, concurrency, UTC or RLS there.
  - Mails are captured by `CapturingEmailSender` (`factory.Mail.LinkToken(to, "reset-password")`).
- Shared setup: `TestHelpers.OrgWithMemberAsync(factory, prefix, settings)` (fresh org + one member) and `TestHelpers.CreateGroupAsync(...)`.
- **Coverage**: `bash coverage.sh` (same folder; extra args go to `dotnet test`) — coverlet collector with `coverlet.runsettings` (migrations excluded) → ReportGenerator (local tool, `.config/dotnet-tools.json`, `dotnet tool restore`) → `TestResults/coverage-report/index.html` (+ `SummaryGithub.md`, `Cobertura.xml`; `TestResults/` is gitignored). Fails below `MIN_LINE`/`MIN_BRANCH` at the top of the script (94 / 78 %, measured 94.7 / 79.0 on 2026-10-15) — raise them when coverage grows, never lower them.

### Frontend (`cd frontend`)

- Type-check: `npm run check` (svelte-check; there is no separate lint step) — keep it at 0 errors **and 0 warnings**
- Unit tests: `npm test` (Vitest, `src/**/*.test.ts`, TZ pinned to Europe/Berlin in `vitest.config.ts`; runs in CI after the check). ## Backend architecture

Layered: **Controller → Service → EF Core `TimeTrackingDbContext`**. Business logic lives in services, never controllers.

- **`ServiceResult` / `ServiceResult<T>`** (`Services/Common/ServiceResult.cs`) is the service→controller contract. Services return `ServiceResult.Ok(data)` or `ServiceResult.NotFound/BadRequest/Forbidden/Conflict(msg)` — they never touch HTTP types. Controllers extend **`OrganizationBaseController`** and call `ToResponse(result)` / `ToCreatedResponse(result)`, which map `ServiceErrorType` → HTTP status + RFC 7807 Problem Details. When adding an endpoint, follow this pattern rather than returning `IActionResult` directly.
- **Authorization is org-scoped via `[RequireOrgRole(...)]`** (`Filters/RequireOrgRoleAttribute.cs`). It reads the `{slug}` route param and checks the caller's `OrganizationRole` (Member ≤ Admin ≤ Owner) on every request (no cache — changes apply immediately) plus the org's `Require2fa`. Org-scoped routes are `api/v{version}/organizations/{slug}/...`. Services start with `_context.FindOrgBySlugAsync(slug)` / `_context.GetOrgRoleAsync(userId, orgId)` (`Data/OrgQueries.cs`).
- **Row-level security (Postgres)**: `TimeEntries` and `AbsenceDays` have a forced RLS policy (migration `EnableRowLevelSecurity`): a row is visible/writable only to its owner and to active members of its organization. `Data/RowLevelSecurity.cs` stamps every connection with `app.user_id` (the authenticated user) or `app.bypass_rls = on` (no HttpContext = trusted system work: migrations, seed, background jobs). Anonymous requests see no rows; code that authenticates a user another way calls `RlsContext.ActAsUser(id)` (the terminal punch). The app must connect as a **non-superuser** role (superusers bypass RLS) — see `docker-compose.production.yml`.
- **Time zones**: instants are UTC (a global value converter normalises every `DateTime`); "which day", "today", "this week" and times in CSV/PDF are the organization's local time via `Services/Common/OrgClock.cs` (`Organization.TimeZone`, default Europe/Berlin). Never use `DateTime.UtcNow.Date` / `DateOnly.FromDateTime(utc)` for business days.
- **Group overrides**: `EffectiveRuleResolver.Combine` is the one rule — a group override replaces the org default in either direction, the most permissive of several groups wins. The member visibility matrix applies it per kind of information (`MemberVisibility.Combine`).
- **Sub-groups** (`Group.ParentGroupId`, same org, max 3 levels, issue #59): `Services/Common/GroupTree.cs` is the one resolution helper — the org's active groups + memberships in one query (`GroupTree.LoadAsync`, or `MemberVisibility.Tree` when a visibility is built anyway). `Effective(id)` fills every setting left on inherit (rule modes, visibility allow/deny per kind and column, core hours mode+window, group-admin capabilities) from the parent's effective value, up to the org default (capabilities: off); the combiners above are always fed `EffectiveGroupsOf(user)` (the effective values of the *direct* groups), so a middle override wins and "most permissive" still spans branches. `ChainGroupsOf(user)` = direct groups + ancestors (shared "own groups", core-hours notice recipients); `AdministersWith`/`ActsFor` = an admin of a group acts for its whole subtree per that group's effective capabilities (approvals, member entries, visibility rights, export, team overview via `AdministeredGroupIds` incl. sub-groups, member management, creating sub-groups). Requests route to `RoutingGroupFor` (nearest group that approves the type and has an admin: own groups, then parents, …; else org admins); approvers = `ApproversOf` along the chain, mailed once. `CheckPlacement` rejects cycles (`group.cycle`) and depth (`group.tooDeep`); `PUT groups/{id}` keeps the parent when `parentGroupId` is left out — the top level is the explicit `moveToTopLevel: true` (with a parent too → 400 `group.parentOrTopLevel`); deleting a parent with sub-groups needs `?subGroups=MoveUp|Delete` (0/1; else 400 `group.hasSubGroups`). Group capability flags are reset to inherit with `inheritCapabilities: ["groupAdminCan…"]`. Org detail member groups and group detail members include inherited memberships with `viaGroupName` ("über Team Küche"). Never re-query groups for a rule — go through the tree.
- **Auth**: refresh tokens and email/reset tokens are stored as SHA-256 only (`TokenService.HashToken`); refresh rotation has reuse detection; backup codes are BCrypt hashes; TOTP steps are single-use. Account deletion anonymizes. Email goes through `IEmailSender` (SMTP via `Email:*`, else `LogEmailSender`).
- **Withdrawing**: the requester may `POST organizations/{slug}/requests/{id}/withdraw` while it is pending (status `Withdrawn`, marked seen, no mail; approvers' open lists are computed from pending rows, so nothing else to clean up).
- **Request approvals** stage their side effects and save them with the status in one `SaveChanges`; `OrgRequest.Status` is a concurrency token, and a side effect that cannot be applied returns 400 and leaves the request pending.
- **Failure entries** (`Services/TimeTracking/FailureEntryService.cs`): a hosted service stops any timer still running at its organization's `BusinessDayEnd` (local time in `Organization.TimeZone`, default 00:00 Europe/Berlin) and sets `TimeEntry.IsFailure`. A failure entry counts as **0** everywhere: `TimeEntryResponse` returns null durations (so every client-side sum skips it), `DailyReportAggregator` (daily CSV, PDF, cumulative overtime) excludes it and marks the day "Needs Correction", and the admin overview reports `FailureEntryCount`. Setting an end time (direct edit or approved edit request) clears the flag. Tests call the static `CloseOverdueEntriesAsync(db, nowUtc)` directly.
- **Core working hours** (`Services/Common/CoreHours.cs`, issues #50/#63): org setting (on/off, local start–end, tolerance, default 09:00–15:00 / 5 min) with group overrides (`Group.CoreHoursMode` null = inherit / Off / Own + times; `Group.CoreHoursToleranceMinutes` null = inherit, independent of the mode; both inherit down sub-groups via `GroupTree.Effective`). Combining over a member's effective groups: `EffectiveRuleResolver.CombineCoreHours` — Off wins, else the intersection (latest start + earliest end on the start day's timeline); `CombineCoreTolerance` — the largest group tolerance, else the org's. **Night windows**: end < start runs past midnight (`CoreWindow.Overnight`/`Utc(day, clock)`); start == end is invalid (`org.coreHoursOrder`). The window belongs to the local day it starts on: working day, holidays, absences/half days of that day; entries across midnight cover it; the check runs after end + tolerance on the next day; the row, calendar marker and compliance day are the start day. Windows are measured in real time (DST nights 1 h shorter/longer, an end in the spring gap moves forward), half days split the real duration. Applies on the member's working days (`WorkingDays.IsWorkingDay`), not on holidays/absences; a half-day absence or half holiday needs only one half of the window (whichever was covered better). Covering = finished non-failure entries in the org + a running timer up to now; Late/Early/Gap beyond the tolerance, or Missing. The failure-entry hosted service's minute loop calls `CoreHours.CheckDueAsync`: every member day from today back `CatchUpDays` (3, org-local) whose window + tolerance has ended and has no `CoreHoursCheck` row (unique per org/user/date; also for fine/exempt days → never twice; RLS like TimeEntries) is evaluated in one batch per org (schedules, absences, holidays, entries: one query each; recipients batched too). A check more than `LateAfter` (1 h) past due is `CheckedLate` — its notice ends in "(checked late)" (inbox: "(nachträglich geprüft)"), mail says "nachträglich geprüft" — and is skipped for a day before the member's org-local join day or a window that started before `Organization.CoreHoursChangedAt` (stamped by every core-hours change, org or group), so switching on never mass-notifies past days. **Backfill**: `coreHoursBackfillDays` (1–31, `org.coreHoursBackfillDays`) on `PUT settings` while switching on, or on `PUT groups/{id}/permissions` with an Own window, sets `Organization.CoreHoursBackfillFrom`; the next loop run flags exactly the days from there whose window started before the change (`Backfilled`, never notified, not before joining) and clears it — enqueued instead of run in the request so it is system work outside RLS and cheap for 31 days; tests call `CheckDueAsync` right after the PUT. Violations notify (in-app `CoreHoursViolation`, `RelatedEntityId` = member, + mail) the member, org admins/owners and the admins of the member's groups and their ancestors (once each) — with `MemberTimeEntryVisibility` off only the member and the admins of those groups whose effective `GroupAdminCanViewAllTimeEntries` is on. The compliance endpoint (`coreHours*` fields incl. `coreHoursBackfilled`, calendar ⚠ marker) and the daily CSV/PDF status re-evaluate stored violations against the current entries (`OpenViolationsAsync`), so a corrected day loses its marker. UI: org settings (backfill checkbox `CoreHoursBackfill.svelte` while off, "endet am Folgetag" hint), group permissions (window, tolerance with "geerbt von …", backfill while not Own). Tests call `CheckDueAsync(db, nowUtc)` directly.
- **Terminal** (`ApiKeysController`, `Services/ApiKeys/`, device contract in `docs/TERMINAL.md`): org-scoped API keys for unattended devices (RFID scanner); the key's `Name` is the terminal name in the protocol and on entries. `POST /api/v1/terminal/punch` is `[AllowAnonymous]` (rate-limit policy `Terminal`, 120/min per hashed key) and checks `X-Api-Key` itself (SHA-256 lookup); keys never yield a user principal. A member holds several `BadgeCard`s (only `CardHash` = SHA-256 of the normalised value via `CardIds`, plus a 4-char `CardHint`; never store/log/return full card values), which admins add/label/block/delete; leaving the org or deleting the account deletes them. Every scan reaching the card lookup writes a `TerminalPunch` row (Started/Stopped/ClosedFailure/Repeated/UnknownCard/Blocked/Rejected; retention 400 days in `RefreshTokenCleanupService`; the member's own punches are in `GET Auth/me/export`) — the double-scan guard, the queued-scan order check, the unknown-card budget (per key / 10 min → 429) and `clientPunchId` idempotency all read that log. Double-scan window (default 60 s), offline window for queued `scannedAt` (72 h) and unknown-card budget (20) are **org settings** (`Organization.Terminal*`, ranges in `TerminalLimits`, edited in the Terminal section). Queued scans pass `scannedAt` into `ITimeTrackingService.StartAsync/StopAsync(atUtc)` or close a recent failure entry. Cards and the punch log have **no RLS** (org admin data like API keys; admin access is `RequireOrgRole`), so the anonymous punch writes them without a bypass; the time entry itself is reached by `RlsContext.ActAsUser(member)`. `TimeEntry.Source` (App/Terminal/Manual/Import/Admin) is set by every path that creates entries; list responses fill `terminalStartName`/`terminalStopName` via `TerminalNames.FillAsync` (one query per page).
- **Personnel number** (#54): optional `UserOrganization.PersonnelNumber` (≤ 50 chars, unique per org — unique index, NULLs distinct), set by admins via `PUT organizations/{slug}/members/{id}/personnel-number` (empty clears; 409 `org.personnelNumberTaken`), shown on the org detail to admins only, exported in the payroll CSV's first column and in the member's own `GET Auth/me/export`. Removing a member (or deleting the account) clears it so the number can be reused — the payroll CSV lists active members only, so no past period needs it (migration `ClearPersonnelNumbersOfFormerMembers` cleared old rows).
- **`ActiveUserFilter`** is a global filter rejecting requests from deactivated users on every authenticated call, and tokens whose `sst` claim no longer matches `User.SecurityStamp` (rotated on password change/reset and account deletion → every session ends at once; cached 30 s, cleared by `AuthService`). Skipped on `[AllowAnonymous]` endpoints.
- **Error codes**: every error ProblemDetails carries a stable `code` (`Services/Common/ErrorCodes.cs`, looked up from the exact English message — `ErrorCodeTests` fails when a listed message is reworded). The frontend translates codes in `src/lib/i18n/messages/errors.ts` and falls back to `detail`. New user-facing messages: add them to both.
- **Pauses**: `PauseRules.ApplyAsync` recomputes the automatic pauses of the entry's whole local day (ArbZG §4: highest exceeded rule, gaps ≥ 15 min and `PauseIsManual` pauses count, the deficit sits on the day's longest automatic entry). Any path that sets a pause explicitly sets `PauseIsManual = true`. New orgs get 6 h → 30 min / 9 h → 45 min.
- **Edit history**: `TimeEntryChanges` rows are written by `TimeTrackingDbContext.SaveChangesAsync` itself (`Data/TimeEntryHistory.cs`) for every finished-entry change — don't add history code to services; set `EntryChangeKindOverride` for approvals.
- **Closed periods** (issue #57, `Services/Common/ClosedPeriods.cs`): org admins close whole months (`ClosedPeriod` rows; `POST organizations/{slug}/closed-periods {from,to,reason?}` closes every month in the range that has **ended** in the org's time zone — the current month only from the day after its last day, never a future one, ≤ 24 at once, `period.notEnded`; `POST …/closed-periods/reopen {month, reason}` needs a reason; `GET` gives every member the months and admins the audit list `ClosedPeriodEvent` Closed/Reopened/AdminChange, newest 200). Org detail carries `closedMonths`. **The one guard** is `ClosedPeriods.GuardAsync`, run by `TimeTrackingDbContext.SaveChangesAsync` for every non-system save: any added/changed/deleted `TimeEntry` (org-local start day, before and after the change), `AbsenceDay` or `WorkSchedule` (the days whose target changes — a new period's range, a changed end only from the earlier end on) touching a closed month throws `PeriodClosedException` → 409 ProblemDetails with `code` `period.closed` and extension `month` (`yyyy-MM`) — unless the signed-in caller is an org admin/owner of that org **and** sends the header `X-Change-Reason` (URL-encoded, ≤ 500); without it 409 `period.reasonRequired`. Admin saves flag their history rows (`TimeEntryChange.InClosedPeriod` + `Reason`) and add one AdminChange event per org/month (member, `Summary` "TimeEntry:2,AbsenceDay:1"). So every write path is covered without code of its own (timer, manual entries, member corrections, imports, request approvals, absences, schedules, terminal) — never add per-endpoint checks; new date-bound entities that change a month's figures belong in `Collect`. Exceptions: stopping a running timer (also a terminal stop), and system work (no HttpContext: the business-day-end auto-stop still stops a timer in a closed day; core-hours checks only read). Requests: `EnsureRequestOpenAsync` refuses a member's new request touching a closed month (an admin's auto-approved absence needs the reason up front); pending ones carry `closedMonth` in the inbox/request lists, a group lead's approval is refused by the guard (org admins approve with a reason; declining is always possible). The terminal turns the exception into a `Rejected` punch (409 `period.closed`, queued `scannedAt` scans and failure closes included; it acts as the member, so never as admin). Not locked: holidays (org-wide, admin-only), the initial overtime (no date), pause rules and the org time zone. No RLS on the two tables (org admin data like API keys). Frontend: the reason prompt is generic — an axios interceptor in `apiClient.ts` answers `period.reasonRequired` with `promptDialog` (`stores/confirm.svelte.ts`) and resends with the header; `utils/closedPeriods.ts` (`closedMonthSet`, `isClosedDay`, `entryLock`, `formatMonth`); `ClosedPeriodsPanel.svelte` in Allgemein; `LockIcon` on closed days in `MemberCalendar`/team calendar, `EntryRow locked` (no actions) and no add buttons for non-admins, notices in the day details, flagged rows in `EntryHistory`, the hint (and a disabled accept for leads) in `/inbox`.
- **Limits**: entry times via `EntryTimes.Validate` (year ≥ 2000, ≤ 24 h, not in the future), export/report ranges via `EntryTimes.ValidateRange` (≤ 731 days), imports ≤ 1000 rows. Invitations (`InvitationService`, mailed `/invite?token=`) are the only way to add members.
- **Auth**: JWT bearer + refresh tokens (`TokenService`), BCrypt password hashing, TOTP 2FA (`TotpService`, Otp.NET). `RefreshTokenCleanupService` is a hosted background service. Get current user id in controllers via `GetCurrentUserId()`.
- **Permissions model** (`Models/Organization.cs`): `RuleMode` (`Disabled`/`RequiresApproval`/`Allowed`) gates actions like editing past entries, pause edits, CSV import, schedule changes; set at the **organization** level and **overridable per `Group`** (`Models/Group.cs`, null = inherit). Groups also carry granular "GroupAdmin can…" capability flags (sub-groups, visibility and approval routing: see below).
- **Member visibility matrix** (`Services/Common/MemberVisibility.cs`, issue #60): what a normal member sees about each colleague, per kind of information (`MemberInfo` flags: Member (+ org role, always shown with the person), Email, Groups (+ group admin), Presence, Vacation, SickDays, OtherAbsences, AbsenceNotes, VacationBalance, WorkSchedule, TrackedTime) and per column — *in own groups* (viewer and person share ≥ 1 active group, ancestors of both sides' groups included) / *outside*. Stored as `Organization.VisibleInGroups/VisibleOutsideGroups` and per group `VisibilityAllow…/VisibilityDeny…` (a kind in neither = inherit); the API speaks rows `{ kind, inGroups, outsideGroups }` (`visibility` on settings, org detail, group permissions, effective permissions). **The data owner's groups decide**: the person's groups' overrides are combined like `EffectiveRuleResolver.Combine` (override replaces the org default, most permissive wins), and nothing is visible about a person whose `Member` is hidden. Members always see themselves; org admins see everything, tracked times only with `MemberTimeEntryVisibility` (still the admins' switch); group admins keep their capability rights over their groups' members (always name/email/groups; approve absences → absence kinds, notes, balance; view all entries → times, schedule, presence; export → times, schedule; manage members → every member's name). Build it once per request (`MemberVisibility.ForCallerAsync(db, org, caller)`, two queries) and ask `Can/Ids/Check`; every endpoint showing other people goes through it — org detail/`mine` counts (the directory has no count for orgs the caller is not in), group lists, absences (+ notes, "entered by" name), time overview, member entries, balance/reports/compliance/export, member work schedules (open to members now), entry history and my-requests names. Hidden people are omitted (no counts), a direct request is 404, a visible person's hidden kind 403. The old `VacationVisibility`/`SickDayVisibility`/group `TimeEntryVisibility` were migrated (`MemberVisibilityMatrix`) and dropped. Frontend: `VisibilityMatrix.svelte` (org switches / group inherit-allow-deny / read-only), `utils/visibility.ts` (preview sentence, `canSee(member, kind)` from the org detail's `visibleInfo`).
- **Team overview** (`GET organizations/{slug}/team-overview`, issue #61): the dashboard's team cards for org admins (everyone) and group admins (the members of their administered groups and all sub-groups, `AdministeredGroupIds`), 403 for everyone else. Balance/failure count/today's core-hours violation need `TrackedTime`, presence needs `Presence` (via `MemberVisibility`) — a card with neither says "Keine Details freigegeben", and the "x von y anwesend" count only counts members whose presence is visible; the balance is `DailyReportAggregator.BalancesAsync` — the balance endpoint's number for the whole team in 4 queries (`BuildRows` is the shared day loop), and `CoreHours.OpenViolationsAsync` has a batched overload. ~9 queries for 50 members, also for a department lead over 3 levels (`TeamOverviewPostgresTests`). Frontend: `TeamOverview.svelte` (polls every 60 s while visible, renders nothing on 403), sort/filter in `utils/team.ts`; "Teamkalender" in the nav and on the dashboard → `organizations/[slug]/absences`. The inline nav links show from `lg` (bottom bar below), the brand text hides between `lg` and `2xl`, the user menu shows an icon instead of the name below `xl`, and the org switcher may shrink (its name truncates) so it never runs into the links at 1024 px.
- **Organigramm** (`GET organizations/{slug}/org-chart`, issue #66, every member): `OrganizationService.GetOrgChartAsync` returns all active groups (parent id, `canManageMembers` = org admin or `AdministersWith` member management) and every person `MemberVisibility` shows (hidden people omitted, so never counted) with org role, direct memberships (`isLead`), `email`/`groups`/`present` null where hidden and `visibleInfo` — **5 queries** however large (`OrgChartPostgresTests`, 100 members). Presence uses the team overview's rule (shared `RunningSince`: running, non-failure timer, `Presence` visible). **Balances are not in it**: the person card asks `GET members/{id}/balance` for the one person clicked (same `TrackedTime` check, `cumulativeOvertimeHours` = the team overview's number) — computing everyone's balance would add the team overview's 4 history queries to every chart open. The team calendar takes `GET absences?groupId=` (group + sub-groups; non-admins only people whose `Member`+`Groups` they see, so the filter never reveals a hidden membership; unknown → 404 `group.notFound`). Frontend: `organizations/[slug]/chart` (tab "Organigramm", links from members/groups), helpers in `utils/orgChart.ts` (`buildOrgChart` → org → groups → sub-groups → people, "Ohne Gruppe" and "Gruppen verborgen" nodes, people in several groups appear in each; `initialExpanded` collapses above 30 people; `searchChart` opens the path to matches; `visibleNodes` + `treeKey` = the ARIA tree keys; `personGroups` "über …"; `groupRules` = effective rules with their source, from `groups/permissions` + org detail, loaded on the first group opened). One markup for both layouts: from `md` a left-to-right drawing (CSS connector lines, CSS `zoom` with +/−/Einpassen, auto fit-width on load) with a side panel, below `md` an indented list with the Modal as bottom sheet. `?group=` on `/absences` (group picker, deep link) and on `/groups` (opens that group), `?user=` on `/absences`.
- **DbContext** (`Data/TimeTrackingDbContext.cs`): entity config branches on `Database.IsInMemory()` (e.g. `HasDefaultValueSql("CURRENT_TIMESTAMP")` only applies for Postgres). Soft deletes use `IsActive` global query filters. `DbSeeder` seeds demo data; `DesignTimeDbContextFactory` forces the Npgsql provider for `dotnet ef` even when dev config is in-memory.
- **API versioning**: URL-segment (`Asp.Versioning`), default v1. **Logging**: Serilog → Console + Seq (:5341) + rolling file (`logs/`). **Rate limiting**: fixed-window policies `AuthStrict`/`AuthModerate`/`General`/`Terminal`; `UseRateLimiter()` sits after `UseAuthentication()` so `General` (300/min) is per user, not per IP; `RateLimiting:GeneralPerMinute` overrides it (3000 in `appsettings.Development.json`, so full e2e runs fit), `RateLimiting:AuthStrictPerMinute` the login limit (10 per IP; 200 only in Development, `RateLimitConfigTests` pins production).

### EF Core migrations
Migrations are **auto-applied on startup** (`context.Database.Migrate()` for Postgres; `EnsureCreated()` for in-memory). You only need to *create* them: `dotnet ef migrations add DescriptiveName` (from `backend/`). See `backend/EF_COMMANDS.md`.

## Frontend architecture

- **Generated API client** (`src/lib/api/`) is produced by openapi-generator (typescript-axios) — **do not hand-edit**; change the backend and re-run `npm run generate-api`.
- **`src/lib/apiClient.ts`** wires the generated `*Api` classes to a shared axios instance: injects the `Bearer` token from `localStorage`; on a `401` (except from the auth endpoints) `authRefresh.ts` exchanges the refresh token **once** — concurrent 401s share that single refresh — stores the rotated tokens via the auth store and retries each request once. Only a failed refresh (or a retry that is still 401) clears auth and redirects to `/login?next=<path>`; login sends the user back to `next`. Import the typed singletons (`authApi`, `timeTrackingApi`, `groupApi`, …) from here, not from `$lib/api` directly. API base URL comes from `PUBLIC_API_BASE_URL`, falling back to the page's own origin: the browser always talks same-origin (Caddy routes `/api/*` in production, the Vite dev/preview proxy forwards `/api` to :7000), so the CSP is `connect-src 'self'` in every mode — a `vite build` next to a running dev server can no longer break it.
- **Client-only rendering**: `src/routes/+layout.ts` sets `ssr = false` (tokens live in localStorage). The root layout renders protected pages only once authenticated (otherwise a spinner while redirecting), so pages never fire API calls signed out.
- **i18n** (`src/lib/i18n/`): German is the default, English via the DE/EN toggle (nav + `/settings`); the choice is stored under the shared `wl-locale` key (`stores/locale.svelte.ts`, also applied to `<html lang>` by the pre-paint script in `app.html`). Components call `t('ns.key', params?)` / `tp('ns.key', count)` — never hardcode either language. Keys are typed dotted paths; runtime fallback is active language → German → the key. Dates/numbers go through the locale-aware helpers in `utils/formatters.ts` (`formatDate`, `formatDateTime`, `formatNumber`, `dayNamesShort`, … → de-DE / en-GB); never `toLocaleDateString('en-US')` or `toISOString().split('T')[0]` (use `dateKey()` for local YYYY-MM-DD keys).
  - **Layout**: one folder per namespace, `messages/<ns>/de.ts` (`export const de = {…}`) + `messages/<ns>/en.ts` (`import type { de } from './de'; export const en: typeof de = {…}` — a missing or extra English key is a type error). `i18n/de.ts` assembles every namespace into `de` (and `Dictionary = typeof de`, from which the key types come), `i18n/en.ts` into `en: Dictionary`.
  - **Only the active language is loaded**: German is in the app shell (default + fallback); `en.ts` is imported **only** by `i18n/dictionaries.ts` via dynamic `import()`, so English is its own chunk (~72 kB raw / 22 kB gzip; the shell shrank from 461 to 391 kB raw). `locale.set()` awaits `loadDictionary()` before switching (no raw keys, one re-render; a later choice wins over a slow load; a failed load keeps the current language), and the root `+layout.ts` `load` loads the stored language before the first render. Never import `i18n/en` or `messages/*/en` statically from app code (type-only imports are fine). `errorHandler`/`formatters` check key existence against `de` — fine, it is bundled anyway.
  - **Adding a namespace** (e.g. `reports`): create `messages/reports/de.ts` and `messages/reports/en.ts` as above (copy any existing folder, e.g. `messages/timer/`), then add one import + one entry to each of `i18n/de.ts` (`import { de as reports } from './messages/reports/de';` … `reports,`) and `i18n/en.ts` (`import { en as reports } from './messages/reports/en';` … `reports,`). Nothing else: `npm run check` enforces the shape, `i18n.test.ts` the rest. **Adding a key**: add it to both files of its namespace.
  - **Tests**: `i18n.test.ts` checks DE/EN key parity, no empty strings, matching `{placeholders}`, that every literal `t('…')`/`tp('…')` key in `src/` exists, and that English is not imported at startup in German. `src/test-setup.ts` (vitest `setupFiles`) preloads English so unit tests can `locale.set('en')` and assert on the next line; a test needing a fresh app calls `vi.resetModules()`. The e2e `language.spec.ts` switches DE → EN → reload → DE and fails on any raw `ns.key` on screen.
- **State** uses Svelte 5 runes in `.svelte.ts` files (`src/lib/stores/`): `auth.svelte.ts` (login/2FA/tokens, persisted to localStorage), `orgContext.svelte.ts`, `theme.svelte.ts`, `locale.svelte.ts`, `timer.svelte.ts` (the running timer shared by nav pill, dashboard and timer page), `toast.svelte.ts` (`toast.success/error(err, fallback)` — use it instead of swallowing errors), `confirm.svelte.ts` (`await confirmDialog({...})` — never native `confirm()`). Stores expose `get`-only accessors over internal `$state`.
- **UI building blocks** (`src/lib/components/`): `Modal.svelte` (native `<dialog>`: focus trap, Esc, labelled title) for every overlay; `ConfirmDialog`/`Toaster` are mounted once in the root layout. Colours come from `utils/colors.ts` (day-type/absence classes, per-person accents, group colour presets, `tintStyle` for user-picked colours) — no hardcoded Tailwind palette classes or hex values, so dark mode works.
- **Groups page** (`organizations/[slug]/groups`): a tree (nested lists with disclosure buttons, `utils/groupTree.ts`: `buildGroupTree`, `parentOptions` for the parent picker — not itself/its subtree, fits 3 levels — and `inheritedFrom` for the "geerbt von Abteilung Gastro: Erlaubt" hints under every inherited setting). Permissions load all groups' overrides (`groups/permissions`) to walk the chain; `VisibilityMatrix` group mode takes the inherited rows as `org` plus `inheritedSource`. `GroupTags` dashes inherited memberships and says "über …" at size sm.
- **Permissions**: `utils/orgRules.ts` mirrors backend rules client-side; `isOrgAdmin(role)` for Owner/Admin checks, and the `can…(...sources)` helpers take `(effectivePermissions, orgDetail)` so group overrides (`groupApi…EffectivePermissionsGet`) win over org defaults.
- **Navigation & pending work** (issue #62, review in `docs/UX_REVIEW.md`): the top nav holds the everyday places (Dashboard, Zeit, Verlauf, Teamkalender, Anfragen for approvers = org admins/group admins, Organisation); below `lg` a bottom bar (Dashboard, Zeit, Verlauf, Team, Mehr) replaces it. Administration lives in the Organisation sections of `organizations/[slug]/+layout.svelte` (Allgemein = `general` for admins only: name/slug/description/website, time zone, business day end, delete with typed name; Mein Arbeitszeitmodell, Mitglieder, Gruppen, Regeln & Sichtbarkeit = `settings`, Feiertage, Terminal = `terminal`, Export = `export`; `/export` redirects there; the layout selects the slug's org). Everything pending comes from one store, `stores/inbox.svelte.ts` (approvals, decisions on own requests, own open requests, notices, failure entries; `count` is the bell badge), shown on `/inbox` with inline accept/decline. The rules page is grouped by `settingTopics()` (`utils/orgRules.ts`); members see `appliedSetting()` ("Für dich gilt"). Dashboard: for leads (`TeamOverview` has data → `bind:available`) own figures left and team right from `lg`, stacked below; key figures today / week / total / remaining vacation (org detail's own member row, only with vacation days set). Quick actions (`/history?date=…&do=add|absence` opens the add form / absence dialog via `MemberCalendar`'s `focusAction`; three across from `md`, stacked in the narrow column beside the team from `lg`) and `OnboardingChecklist` (`utils/onboarding.ts`, auto-ticked, dismissal + "seen" flags per user/org in localStorage). Page loads use `Skeleton.svelte`, empty lists `EmptyState.svelte`; muted text is `text-base-content/70` at most (AA), touch targets are ≥ 44 px under `pointer: coarse` (components.css).
- **Public routes** (no login): `/login`, `/register`, `/forgot-password`, `/reset-password?token=`, `/verify-email?token=`, `/health`; everything else waits for auth (`/invite?token=` sends signed-out visitors through login/register via `?next=`, `utils/redirect.ts`).
- **Errors**: `extractErrorMessage` (`utils/errorHandler.ts`) translates the backend `code` first, then shows `detail`, then the fallback.
- **Calendars**: `use:dayPress` (`utils/dayPress.ts`) — left click/Enter selects a day and shows its entries below, right click / long press opens the day dialog. `EntryRow` (its editor) has a member mode for admin corrections; `EntryHistory` shows an entry's "Verlauf". Balances shown in the UI come from `GET organizations/{slug}/members/{id}/balance` — never recompute overtime in the browser.
- **Routes** (`src/routes/`) are file-based; org features live under `organizations/[slug]/` (absences, groups, holidays, members, settings, terminal, export, time-overview) and (re)load in an `$effect` keyed on `page.params.slug` (use `page` from `$app/state`, not `$app/stores`). `/history?date=YYYY-MM-DD&entry=<id>` opens that day and the entry editor (the failure-entry banner links there). Shared UI in `src/lib/components/`, helpers in `src/lib/utils/`.

- Seeded dev logins (in-memory DB): `max.mueller@example.com` (Owner), `anna.schmidt@example.com` (Admin), `tom.weber@example.com` (Member, with a demo failure entry) — all password `Password123`.
